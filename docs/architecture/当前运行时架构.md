## 6. 当前 Path A Implementation 与 REQUIRED Path B 主流程

当前 `batch_draft_save` 的生产步骤来自 `BATCH_DRAFT_SAVE_STEPS`，它明确排除旧半托管步骤。当前已接入的 Path A Implementation 是：

```text
持久任务与当前队列 CAS
  → 当前 job / lease / snapshot / command JIT
  → 打开精确 Path A editor
  → 全字段零写预检
  → 按冻结 binding 填写并逐字段读回
  → 保存前再次 JIT / ledger 原子复核
  → 点击精确“保存”
  → SAVE ActionResult
  → VERIFY_NOT_PUBLISHED
  → 三铁证入账
  → 下一商品
```

这段代码事实只能证明 Path A 的工程接线，不能代表完整产品。完整成功的 REQUIRED 主流程应为：

```text
当前队列/JIT/可见会话/商品身份
  → 动态类目目录定位目标叶子
  → 当前页面 categoryId/Schema/capability 零写复核
  → 持久 preimage + rollback preparation
  → 主编辑字段与模板填写
  → 产品视频执行并精确读回
  → SKU/批发规则执行并精确读回
  → 所有自然语言生成完成后执行翻译并做英文验证
  → 主编辑全字段预检/读回
  → Path B 主保存意图与半托管提示 Modal
  → 点击“编辑半托管信息”，由店小秘自身执行原生门；系统禁止资格预检
  → 按真实 network/page/ledger 事件闭合实际主编辑 SAVE 与门 outcome，不预设固定先后
  → 受限中间“继续发布”动作（仅原生门 admitted 且该精确 Modal 出现）
  → /web/smt/editFromSmt 页面身份与 Schema 复核
  → SAVE1 verified + gate admitted + page bound 三者 join
  → 国家、货品、变种/JIT 填写与读回
  → Path B 第二次授权与半托管保存
  → 两段保存证据 + 独立未发布证明
  → 下一商品
```

每件商品必须执行视频、翻译、批发和半托管，不允许以 `disabled`、`not_applicable`、空动作或 `SKIPPED_BY_FROZEN_PLAN` 计为成功。某店铺、类目、商品或页面不支持任一 REQUIRED 能力时，应在首个写动作前阻断整个商品。rollback preparation 同样每件必经：在任何字段修改或外部 mutation 前持久保存可验证 preimage 和恢复计划；实际 restore 只在适用失败路径触发，成功商品不会被反向撤销。

上游 Path B 的中间按钮虽然包含“继续发布”字样，但产品已裁决允许自动化。该允许只适用于精确的 Path B 欧盟外包装确认 Modal，并须同时绑定当前商品、当前页面、预期 Modal 文案、预期后续只读/检测请求和 `/web/smt/editFromSmt` 跳转。它不是字符串白名单；最终发布、“立即发布”“保存并移入待发布”及任何最终上线请求仍永久禁止。

半托管资格只由点击可见“编辑半托管信息”后的店小秘原生门裁决。`verifyPopChoiceShop` 只能作为平台自身动作的被动网络证据，本系统不得主动调用、重放或从店铺/类目/历史事实推断结果。当前运营文字还不能证明实际 SAVE1 请求一定先于原生门闭合；真实 Adapter 在取得有序事件证据前保持 `BLOCKED`。

真实动作的 Interface 分散在：

- `execution/browser_agent_protocol.py`：command/target/page/action 合同；
- `execution/browser_agent_worker.py`：持久 worker、动作时复核；
- `execution/batch_command_contract.py`：批次 SAVE/VERIFY 上下文；
- `execution/mutation_dispatch_ledger.py`：写前账本与崩溃窗口；
- `execution/action_result_contract.py`：页面、读回和三铁证消费；
- `batch_edit/frozen_execution_contract.py`：冻结值到执行 payload；
- `execution/v1_runner.py`：任务顺序、失败、UNKNOWN 与报告。

任何真实派发后结果不确定都必须落 `UNKNOWN` / `needs_manual_review`，后续 job 保持未派发；不得自动重试。视频生成或其它会消耗额度、创建远端资源的动作也属于外部 mutation，派发不确定时遵守相同规则，不能声称已 rollback。

## 7. 证据与安全层

成功不是一个布尔值，而是同一 task/job/action/target/snapshot/runtime identity 下的组合事实。完整 Path B 商品至少要分别核算主编辑保存与半托管保存，并形成：

1. 预期保存回包业务成功；
2. 页面成功态；
3. 独立未发布读回；
4. mutation ledger 已闭合；
5. command、读回字段集合与冻结 payload 精确对应。

此外还必须记录视频、翻译、批发、rollback preparation 的逐项 before/after、执行状态和精确读回；缺任一 REQUIRED 能力证据，该商品不得成功。两段保存共用同一冻结商品身份，但各自需要独立的 command、JIT/lease、ledger 和业务回包；最终独立未发布证明要覆盖整个 Path B 结果。

`PublishGuard`、任务启动闸、BrowserAgent page/target contract 和前端禁用是独立防线。前端只负责 UX；后端必须从持久任务和实时会话重建事实，不能相信调用方自报的 mode、hash 或页面身份。中间“继续发布”例外应由单独的 Path B transition Interface 判定，不应通过放宽通用 PublishGuard 实现。

新增的 `services/evidence_collector.py` 当前只是内存容器，未绑定文件、hash、task/job/action 或 ledger，不属于正式三铁证 Module。

## 10. 架构深化方向

以下是当前最高 Leverage 的深化机会，尚不是已完成重构：

1. **FullProductEdit Module（P0）**：用一个深 Interface 编排 rollback preparation、主编辑、视频、批发、翻译、Path B 两次保存和证据；当前这些规则分散在 Runner 与多个浅 Implementation 中。
2. **ControlledSaveDispatch Module（P0）**：把 route、Runner、worker、lease、queue CAS 与 ledger 的动作时授权收进一个深 Interface，减少安全合同分散，并明确两次保存各自的事务事实。
3. **CanonicalSaveReceipt Module（P0）**：统一 producer/consumer 的字段读回、两段 SAVE/VERIFY、三铁证和持久证据，删除浅层 `EvidenceCollector` 平行实现。
4. **CategoryCatalog Module（P0）**：把版本化任意深度目录、path↔leaf、目录 hash 与 live page/Schema 漂移比较收进一个 Interface；缓存 Adapter 和可见页面 Adapter 在该 Seam 提供不同来源，执行以 live 事实为权威。
5. **RollbackSafety Module（P0）**：集中持久 preimage、逆序恢复、恢复读回和 mutation 后 UNKNOWN 语义，避免各填写器自定义“回滚成功”。
6. **DxmWorkflowAdapter 外部 Seam（P1）**：保留 Adapter Interface，把 `DxmLoginFlow` 拆为 VisibleSession、ReadOnlyCatalog、EditorPage、RequiredCapabilityExecutor、SaveProofProducer 等深 Implementation。
7. **PlanSnapshotLifecycle Module（P1）**：统一 Reader → sync → preview → freeze → task → execution payload，避免 facade 与 store 重复解释快照。
8. **RuntimeTruth Module（P1）**：统一 `live-status`、`runtime/status`、login reason code、Reader readiness 与前端 next action，避免同一会话出现两套登录真相。

目标不是增加更多文件，而是提升 Depth 与 Locality：安全不变量应在少数深 Module 内完成，页面与 route 只消费稳定 Interface。
