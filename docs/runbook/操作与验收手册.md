### 2.3 `DXM_SAME_DATA_RUNTIME`

该错误表示另一个 DXM Agent Console 实例仍持有同一数据目录。它是保护数据库、会话和写入账本的互斥门禁，不应自动杀进程或接管。

处理顺序：

1. 回到原 DXM 窗口，确认没有 `running`、`pause_requested`、`stop_requested` 或待人工对账任务。
2. 从原窗口正常退出，等待后端进程结束。
3. 若原窗口已丢失，先按错误页给出的 PID 做只读核对：

```powershell
Get-CimInstance Win32_Process -Filter "ProcessId = <PID>" |
  Select-Object ProcessId, Name, ExecutablePath, CommandLine
```

4. 只有确认 PID 属于本项目旧实例、没有真实任务且已记录现场后，才显式结束该 PID：

```powershell
Stop-Process -Id <PID>
```

5. 重新打开一次。不要同时启动源码版、目录版和 portable 指向同一数据目录。

## 4. 完整 Path B 真实验收（当前 BLOCKED）

当前状态不允许把下面步骤当普通用户操作。完整 L0 已于 2026-08-28 清零，但只有 [BLOCKED](../../BLOCKED.md) 中其余生产接线、固定源码/同源 package、真实页面负向测试和人工授权门禁全部关闭，才可由有权限人员执行：

1. 从同一 UI、同一可见会话创建新的三商品 snapshot/task；不得复用历史 task。
2. 记录 Git/worktree/build/package/runtime/data identity。
3. 对每件商品确认目标为目录中的真实叶子，并验证视频、翻译和批发的当前可观察能力；半托管资格不得预检，只能由稍后点击 `OPEN_SEMI_MANAGED_EDITOR` 后的店小秘原生门裁决。任一可在首写前确认的 REQUIRED 能力不支持就停止。
4. 先用 hash-only PrepareRequest 经 `POST /api/real-dxm/path-b/scopes/derive-and-prepare` 派生并注册当次外部 scope；导入既有 scope 时才使用 `/scopes/prepare`。只有冻结 snapshot 已权威给出每件商品精确且完整的 `real_write_stage_fields.SAVE1/SAVE2` 分区，且覆盖全部 resolved/preimage 字段时才可签发；阶段由调用方自报、缺字段或多字段一律拒绝。再把同一 scope 与对应 ApprovalFile 一并提交给 `POST /api/tasks/{task_id}/approve-and-start`。scope 消费、6 张 child lease、手工授权和 task `draft → running` 必须在同一 SQLite 事务完成；任一失败整体回滚。
5. Runner 串行处理。每件先复核当前页面商品、店铺、categoryId、Schema 和 capability；如需切类目，必须从可见 UI 切换后重新读取，目录缓存不能覆盖 live 漂移。
6. 在任何页面修改或外部 mutation 前持久化 preimage 和 rollback plan；预检所有稳定 binding、可见控件和目标值。
7. 填写主编辑字段，实际执行视频、SKU/批发和翻译；翻译位于所有自然语言生成完成之后。逐项精确读回，任何 REQUIRED 能力不得记为 skip。
8. 完成主编辑全字段预检后，为最早可能触发 SAVE1 的顶部精确“保存”建立 JIT/lease/ledger，并开启同一多步 FIRST_SAVE handshake；提示 Modal 本身不算保存成功。
9. 在同一 active handshake 下精确点击 `OPEN_SEMI_MANAGED_EDITOR`，只观察店小秘原生门 admitted/rejected/unknown；不得主动调用或重放资格接口。按真实 network/page/ledger 事件分别闭合 SAVE1 与门结果，不硬编码二者墙钟先后。
10. 只有 `SAVE1 verified + native gate admitted + same-handshake causal binding` 均成立后，才允许在已验证的特定 Modal 上点击精确“继续发布”（`SEMI_MANAGED_CONTINUE_TRANSITION`）；上下文不完整、门拒绝或任一事实不确定立即停止。
11. 在 `/web/smt/editFromSmt` 重新验证页面身份并完成第二页全量零写预检，再填写和读回参加国家、货品信息、变种价格/编码/JIT 库存等冻结值。
12. 执行第二次独立 JIT/lease/ledger，点击半托管页精确“保存”。当前商品的两段保存和完整未发布证明闭合前不推进下一件。
13. 在真实任务上验证暂停 ≥10 秒、继续不重做、停止不再派发。
14. 任一外部 mutation 派发不确定立即进入 `UNKNOWN`、停批并人工对账；禁止自动重试或声称已 rollback。

永久禁止：主编辑或半托管页的最终“发布”“立即发布”“保存并发布”“保存并移入待发布”及任何最终上线请求。允许的中间“继续发布”不是全局文字白名单，也不授权直接调用写接口。

### 4.1 外部 scope、ApprovalFile 与一次性阶段驱动

真实写 scope 和 ApprovalFile 必须位于 Git 工作树之外。不要把真实店铺、商品、字段值、账号、会话、nonce 或审批原文写入仓库、命令历史、报告或截图说明。scope 只保存受控身份与 hash，并必须满足 [JSON Schema](../../config/real_dxm_write_scope.schema.json)：

- `stage=execute`、`path=B`、有效期尚未过期，且没有通配符；
- 精确绑定当前 clean Git/worktree、backend runtime、browser runtime/session、L2 evidence、account、同一 shop、snapshot 与 task；
- 正式系统流精确绑定同一店铺的 3 个有序商品；每件显式列出字段 preimage/expected hash；
- 每件只有 `SAVE1 → SAVE2` 两张独立单次 child lease，每次最多一个物理 request；
- `publishAllowed=false`，任何 publish-like 字段或发布请求都拒绝；
- ApprovalFile 精确绑定 `scopeSha256 + nonce + expiresAt`，只能在批准事务中消费一次。普通 SHA-256 只证明规范化内容一致，不代替操作员身份认证。
- `DXM_DATA_DIR` 也必须位于 Git 工作树之外；Prepare 的“零写”只表示零真实 DXM mutation / 零 physical SAVE / 零 publish，本地 snapshot/task/scope registry 仍会写外部 runtime DB。API 中的零计数只是路由合同声明，脚本必须在 scope 前后分别读取 task-local `acceptance-export`，确认 receipt/ledger/publish 全为零，不能只信常量。
- Prepare/Shadow 的 plan API 必须使用 `projection=scope_prepare`，只返回可信 `saveStage`、字段 preimage/expected hash 和身份，不返回 `current_value_snapshot`、`resolved_value` 或 Schema 正文。这里的普通 SHA-256 是一致性承诺，不是机密保护；布尔、枚举、低熵价格等仍可能被枚举，不能把 hash 当作脱敏匿名化。

阶段驱动 [run-real-dxm-path-b-system-test.ps1](../../scripts/run-real-dxm-path-b-system-test.ps1) 只能调用公开 FastAPI，不读 SQLite、不直连 Adapter、不操作 DOM；scope、PrepareRequest、尝试计数、trace 和验收产物均写到 Git 外部目录。PrepareRequest 只含方案选择与每件商品显式的 `field + SAVE1|SAVE2 + preimageSha256 + expectedSha256`，其它权威身份全部由当前 backend 派生：

# Discovery scope：fresh Reader → hash-only preview → freeze/task → derive-and-prepare。
# snapshot 必须同源冻结精确 SAVE1/SAVE2 字段分区与两阶段 preimage/expected。

当前源码已实现上述窄系统流的 scope、原子启动、Discovery seal、fresh Formal lineage 与 1+6 receipt 验收合同，并保持严格 fail-closed：Discovery 只允许一个 `FIRST_SAVE_INTENT` command/lease/ledger/native-handshake，在唯一 SAVE1 与独立未发布 VERIFY 后由仓储事务封存 receipt、停止 task，禁止 SAVE2/其它商品；GET 恢复从私有持久权威重建，而不是只信 summary boolean。Formal 在任何 CAS 前要求 fresh snapshot/task/scope/Approval 严格晚于 Discovery seal，绑定 predecessor/receipt，并要求 Discovery after 值与 Formal 首商品 SAVE1 preimage 完全一致。所有阶段必须显式复用上例同一个 `$evidenceDirectory` 与 `$attemptJournalFile`；首次创建 journal 使用独占 `CreateNew`，既有 journal、receipt 与 scope 只允许独占打开和全量复验。POST 已发送但无法证明未受理时一律记为 `UNKNOWN`，不得再试。

这不等于当前可运行：五项 capability 中 `video`、`translation`、`wholesale` 缺真实动作/post-readback，`semiManaged` 缺首写前只读 capability binding，`rollbackPreparation` 的 preimage 读取时序晚于首写 guard；`dxm_info`、`regional_pricing`、`other_info`、`semi_countries` 等 section 也缺权威字段或复杂控件读回。现有 Path B UI 动作仍含历史矩形中心/原生坐标和 DOM fallback，禁止用猜测 selector 或删除 DOM 来补齐。生产 provider 因此在真实写前返回明确 `PRODUCTION_*_NOT_BOUND`。此外，本仓没有可用的当次真实 scope/持久会话，且实现工作树不 clean；本轮没有启动 backend、Reader、浏览器、Shadow、Discovery 或 Formal，真实 mutation / publish / auto retry 均为 0。必须先通过只读 headed Playwright discovery 取得缺失事实、补齐并审阅 producer/executor，再形成 clean HEAD、Git 外 data dir、有效持久会话及 fresh Reader/account/L2，最后才可由操作员签发两份互不复用的 ApprovalFile。全局 `RELEASED_PLAN_EXECUTION_PATHS` 仍只有 Path A。

正式任务完成后，只能从 `GET /api/tasks/{task_id}/acceptance-export` 取得公开验收投影，再交给 `scripts/report/generate_v1_acceptance_record.py` 生成只保留 opaque refs/hash/status/count 的脱敏记录。生成器复验 sealed Discovery 的 1 次 SAVE1/5 个 leaf proof 与 fresh Formal 的 6 次独立 SAVE/30 个 leaf proof，要求 command/lease/proof 不复用、时间顺序和首商品 readback→preimage 连续、每次恰好一个 mutation、零发布、五项能力、writer fence、provenance、`UNKNOWN=0` 和自动重试为零；全部同源才输出 `REAL_PATH_B_3_ACCEPTED`。生成器只能复核公开投影内部一致性；证据来源真实性由 backend 从私有 DB/ledger/command/action-result/receipt 权威重建后负责。证据缺失时 `published` 保持 `null`，不得用“没有观察到发布”伪造 `false`。

## 5. 结果与证据

“保存结果”必须按 task → ordered job → product → action 展示：

- snapshot/hash、队列位置和运行身份；
- SAVE command、mutation ledger 与动作时间；
- 回包、页面成功态、独立未发布证明；
- 逐字段预期/读回；
- 视频、翻译、批发和 rollback preparation 的逐项 before/after 与读回；
- Path B 主编辑保存和半托管保存各自的 command、JIT/lease、ledger、业务回包与页面事实；
- `succeeded`、已知前置失败或 `UNKNOWN/needs_manual_review`；
- HVD、日志、API、SQLite 与报告的一致性。

没有五项 REQUIRED 能力证据、两段保存事实或完整三铁证的商品不得计入成功。旧报告、mock、HTML、手工截图或“未点发布”不能补齐证据。

## 7. 停止与现场保护

- 正常停止：关闭启动器/桌面窗口；有真实任务时先在 UI 安全停止并等待 worker ack。
- 视频生成、主编辑保存、半托管保存等外部 mutation 派发后进程异常：不要重启后自动重试，保留 ledger、日志和页面，状态应为 `UNKNOWN`。
- 首次外部 mutation 前失败：按冻结 rollback plan 逆序恢复页面并精确读回；恢复不完整同样停批。外部 mutation 已派发后不得用第二次写入冒充回滚。
- 不删除 `data/**`、SQLite、runtime lock、证据或日志来“解决”状态冲突。
- 不启动第二个同数据目录实例，不强占正在服务真实任务的 8000 端口。
- 不提交 Cookie、账号密码、token、raw 抓包、真实业务样例或诊断原文。
