## 2. 采集箱选品

### 2.1 读取草稿产品列表

| 数据 | 接口 | 参数 |
|------|------|------|
| 草稿产品 | `POST /api/smtProduct/pageList.json` | `dxmState=draft`，`shopId=-1` 或具体店铺 |

**分页参数**：

| 参数 | 说明 | 示例 |
|------|------|------|
| `pageNo` | 页码，从 1 开始 | `1` |
| `pageSize` | 每页数量，建议 100 | `100` |
| `shopId` | `-1`=全部店，`6517349`=单店 | `-1` |
| `dxmState` | 必须为 `draft` | `draft` |
| `searchType` | 搜索类型（0=默认） | `0` |
| `searchValue` | 搜索关键字 | 空 |

### 2.2 产品列表字段（选品用）

| 字段 | 用途 |
|------|------|
| `id` / `idStr` | 编辑页入口：`/web/smt/edit?id={idStr}` |
| `shopId` | 商品所属店铺 |
| `subject` | 标题（展示用，编辑时改为英文） |
| `categoryId` | 当前类目叶子 ID |
| `productMinPrice` / `productMaxPrice` | 价格区间 |
| `imageURLs` | 缩略图地址（按 `;` 分割取第一张 http 图） |

| `dxmState` | 状态（应为 `draft`） |
| `comment` | 备注（去空白，空则省略） |
| `sourceName` | 来源平台（如 1688 / 拼多多） |

### 2.3 多选操作

| 步骤 | 操作 |

## 6. Path B 专属：主编辑页保存与跳转

### 6.1 主保存前字段条件（平台 op=4 营销检测）

> ⚠️ **Path B 点「保存」前必须满足以下条件，否则被营销检测拦下**：

| 字段 | 状态要求 | 缺失时弹窗文案 |
|------|----------|----------------|
| 营销图-白底图 (1:1) | 必须有 | 「营销图-白底图(1:1)缺失」 |
| 营销图-场景图 (3:4) | 必须有 | 「营销图-场景图(3:4)缺失」 |
| 无线端描述 | 必须有 | 「未生成无线端描述」 |

**解决方案**：使用「一键生成」功能生成营销图和无线描述。

### 6.2 主保存意图与 Path B 原生入口握手

半托管**资格**不做系统预检，但两个可见点击都可能产生第一次 SAVE 的平台下游效应，仍须接受保存安全管控：

| 动作 | 可能效果 | 点击前必须完成 |
|------|----------|----------------|
| `FIRST_SAVE_INTENT`（顶部精确「保存」） | `OPEN_MODAL`、`MAY_DISPATCH_SAVE1` | 在同一事务复核当前批准/队列/运行身份，消费唯一 FIRST_SAVE `save_lease_id`，建立多步 SAVE ledger，并先持久化 `MAY_HAVE_DISPATCHED` |
| `OPEN_SEMI_MANAGED_EDITOR`（精确「编辑半托管信息」） | `NATIVE_GATE`、`MAY_DISPATCH_SAVE1` | 消费独立 `action_grant_id`，同时事务化复核同一 `entry_handshake_id/FIRST_SAVE command`，其 phase 仅允许 `IN_FLIGHT | SAVE_VERIFIED_AWAITING_GATE`；点击前持久化本 action 的 `MAY_HAVE_DISPATCHED`，不得签发第二张 SAVE lease |

两个动作后的真实 SAVE 请求都归属同一个 FIRST_SAVE command，但每条物理 mutation request 仍必须独立记录 request identity/hash、causal action、response 和 ledger sequence。未经真实幂等证据证明为同一次平台保存时，请求数大于 1 必须 UNKNOWN，不能因 command id、URL 或 payload 相同就合并。任一点击后崩溃、超时或证据丢失，均不得恢复成“尚未保存”；只有真实同源证据证明某一动作绝不可能触发 SAVE1，才可在新版本合同中缩小其 possible-effect set。

| 步骤 | 操作 | 结果 |
|------|------|------|
| 1 | 确认营销图和无线描述已具备 | 通过闸门 |
| 2 | 经动作时授权后点击顶部精确「保存」 | 触发半托管提示 Modal；此时不得仅凭 Modal 断言第一次 SAVE 已派发或完成 |
| 3 | 等待「半托管提示」Modal 出现 | Modal 文案：「您已勾选参与半托管服务，为保证您的发品质量，需完善半托管信息」 |
| 4 | 点击 Modal 中的「编辑半托管信息」 | 触发店小秘自身的原生资格检查；尚不能宣称已进入半托管页 |

**Modal 操作**：

| 按钮 | 效果 |
|------|------|
| 「取消」 | 平台观察行为为取消勾选 `isJoinChoice` 并中止本次保存意图；系统必须按网络/ledger 事实确认是否零派发，不能仅凭文案宣称安全取消 |
| 「编辑半托管信息」 | 派发 `OPEN_SEMI_MANAGED_EDITOR` 并触发店小秘原生检查；明确放行后才可能进入后续 Modal 或半托管编辑页 |

**原生门三类结果**：

| 结果 | 系统处置 |
|------|----------|
| 明确放行 | 记录原生门 receipt；还须闭合实际 SAVE1 三铁证并证明同属一个入口握手，才建立 `entry_handshake_joined`；此后如出现已实证特定 Modal，再执行 `SEMI_MANAGED_CONTINUE_TRANSITION`，最终精确绑定 `editFromSmt` |
| 明确拒绝，且已证明第一次 SAVE 未派发 | `outcome_code=semi_entry_rejected_main_not_saved`；零保存停批，不降级 Path A |
| 明确拒绝，且第一次 SAVE 三铁证已闭合 | `outcome_code=semi_entry_rejected_main_saved`；保留部分保存事实，要求人工复核，停批 |
| SAVE1 最终事实、原生门结果或同一握手因果绑定无法证明 | `execution_state=unknown`，停批，不自动再次点击或补偿保存 |

## 8. 保存成功铁证

> ⚠️ **三要素缺一不可**：

### 8.1 主编辑页 SAVE 铁证（生产 Path B 第一阶段）

第一次 SAVE 的真实写请求可能发生在点击顶部“保存”之后，也可能由随后点击“编辑半托管信息”的平台原生握手触发。当前证据尚未确定哪个点击触发，因此两个点击都按 `MAY_DISPATCH_SAVE1` 防护，只能以真实网络、页面和 mutation ledger 观察到的实际派发为准。两组事实只要均已验证且因果绑定同一握手，就不要求还原墙钟全序；无论请求出现在哪个 UI 步骤，三铁证字段和成功标准不变。

| 铁证 | 判定 |
|------|------|
| 业务回包 | `POST /api/smtProduct/add.json` 返回成功 |
| 页面成功态 | Modal「您的产品编辑成功！」或「您的产品编辑成功!」 |
| 未发布证明 | 独立读取商品状态，确认未进入发布/待发布 |

### 8.2 半托管页 SAVE 铁证（Path B 第二阶段）

| 铁证 | 判定 |
|------|------|
| 业务回包 | `POST /api/popChoiceProduct/add.json` → `code=0`，`msg` 含「产品已保存到「待发布」」 |
| 页面成功态 | Modal「您的产品编辑成功!」 |
| 未发布证明 | 未点击「立即发布」，确认半托管品在待发布而非已上线 |

这里禁止的是“保存并移入待发布”按钮及其 action intent；精确半托管“保存”的平台自然结果可以是“待发布”状态，但仍必须用独立读回证明没有上线，不能仅凭回包文案通过。

### 8.3 铁证采集时序

```
主页面全量零写预检、preimage 与动作时授权通过
  → 点精确「保存」，绑定“半托管提示”Modal；不预判 SAVE1 已完成
  → 取得独立 action grant，点精确「编辑半托管信息」
  → 店小秘原生门自动检查；系统只观察真实网络/页面/ledger 事件
  → 分别闭合 native-gate outcome 与实际 FIRST_SAVE 三铁证，不假定二者固定先后
  → SAVE1 verified + admitted + same-handshake causal binding 后才允许必要的中间转换
  → 再绑定正式 editFromSmt 页面身份，才允许第二页首写
  → 明确拒绝按最终 SAVE 事实分成 main_not_saved / main_saved；最终事实或同一握手因果绑定无法证明即 UNKNOWN
```

## 9. 批量循环

### 9.1 循环结构

任务启动前必须取得同店铺系统内 writer fence，并确认 snapshot 未超过 24 小时启动上限；这两个条件都不替代每个动作前的草稿 revision、类目、Schema、catalog 和页面身份实时检查。任一漂移都在任何后续写入前中止，禁止 warning 放行或人工覆盖。

```
for itemId in selectedIds[]:
    open /web/smt/edit?id={itemId}
    close_visible_notices_via_stable_binding()  # 禁止删除 DOM/遮罩
    核验正式 HTTPS 页面、商品、账号、shopId、categoryId、Schema hash、revision 与冻结快照一致
    inspect 主页面 11 分区 + ContentFinalize 全部后置控件（zero write）
    持久化主页面 preimage、恢复顺序和首写前证据

    普通编辑分区的字段策略（§4）
        每个字段按「保持原值 / 方案配置 / 模板」模式处理
        标题检查 128 字符限制
        图片按前 6 张规则选取
        变种自定义名称按规则处理

    for section in 主页面 0..10:
        按冻结字段执行 apply → 立即 readback → section receipt
    end for

    ContentFinalize（视频 → HVD 安全点 → 批发 → HVD 安全点 → 一键翻译 → HVD 安全点）
    聚合所有冻结字段与关系读回

    Path B 入口握手（§6）
        点精确「保存」→ 绑定 Modal → 点精确「编辑半托管信息」
        由店小秘原生门裁决；不得主动预检资格
        分别闭合 FIRST_SAVE 三铁证和原生门结果，不假定固定先后
        SAVE1 verified + admitted + same-handshake causal binding 后才允许中间转换
        再精确绑定正式 editFromSmt identity 才可继续

    在 editFromSmt 重新核验页面/商品/店铺/revision
    inspect S1–S3 全部后置控件（zero write）并持久化第二页 preimage
    for section in S1..S3:
        按冻结字段执行 apply → 立即 readback → section receipt
    end for
    SECOND_SAVE 独立 JIT / lease / ledger / 三铁证

    assert 视频 / 批发 / 翻译 / 半托管 / rollback preparation 均有真实 receipt
    仅当前商品 `execution_state=succeeded` 且最终未发布已证明后进入下一商品；任何非成功终态停止本批，`unknown` 必须立即停批并人工复核
```

### 9.2 每件商品必经能力

| 能力 | 必经结果 | 不可用时处理 |
|------|----------|--------------|
| 产品视频 | 真实生成/选择、投放、视频身份和字段读回 | 首个 SAVE 前 fail-closed |
| 批发配置 | 真实控件、起订/折扣/扣减、价格货值库存关系和读回 | 每件必经；不可用时 fail-closed，不得跳过 |
| 一键翻译 | 所有允许自然语言字段翻译、before/after、英文和越界校验 | 首个 SAVE 前 fail-closed |
| 半托管 | 主保存意图、`OPEN_SEMI_MANAGED_EDITOR`、店小秘原生门、实际主编辑 SAVE、必要的受控转换、`editFromSmt` 填写、第二次 SAVE | 不做本地资格预检；SAVE1/门按真实事件分别取证，拒绝按是否已保存分类，不确定停批，不得降级 Path A |

### 9.3 HVD 控制

| 控制 | 操作 | 行为 |
|------|------|------|
| 暂停 | 点击「暂停」 | 在当前 section receipt 或明确外部动作终态后的安全点生效；不必等整件商品完成 |
| 继续 | 点击「继续」 | 从持久化的下一个安全 section 继续，不重做已验证 SAVE/长动作 |
| 停止 | 点击「停止」 | 不再派发新动作；在途动作先收敛为成功、明确拒绝或 UNKNOWN |
| 急停 | 点击「急停」 | 只记录停止意图并阻止新命令；在途动作进入 `resolving`，不得立即伪造终态 |

`resolving` 期间“继续”禁用，“暂停”延后到证据闭合后的安全点；同店铺不得开始新任务。只有明确成功、明确拒绝或证据期限耗尽转 `UNKNOWN` 才能离开该状态。

## 10. 失败处理

### 10.1 校验失败

| 现象 | 原因 | 处理 |
|------|------|------|
| SAVE 动作前/后出现明确 `.has-error` 且可证明写请求未派发 | 零写预检漏项或页面漂移 | 当前 attempt 终止并记录 reason code；修配置后重新 Reader/preview/freeze/批准，不在原 attempt 内修补重试 |
| 货值 > 零售价 | 价格关系错误 | 当前 attempt 终止；回到方案修正关系，再重新 Reader/preview/freeze/批准创建新 attempt |
| 必填字段为空 | 字段未填写 | 当前 attempt 终止；回到方案补齐映射/值，再重新 Reader/preview/freeze/批准创建新 attempt |

### 10.2 营销检测失败（Path B）

| 弹窗文案 | 原因 | 处理 |
|----------|------|------|
| 「营销图-白底图(1:1)缺失」 | 白底图未生成/上传 | 当前 attempt 阻断；回到方案补齐并重新 freeze，不在 SAVE 后自动修补 |
| 「营销图-场景图(3:4)缺失」 | 场景图未生成/上传 | 当前 attempt 阻断；回到方案补齐并重新 freeze |
| 「未生成无线端描述」 | 无线描述为空 | 当前 attempt 阻断；回到方案生成并重新 freeze |

### 10.3 半托管保存失败

| 现象 | 原因 | 处理 |
|------|------|------|
| 半托管页 SAVE2 前零写预检失败，且已证明 SAVE2 未派发 | 原箱/物流/重量/尺寸/价格/JIT 或稳定 binding 未闭合 | 终止当前 attempt；回到 Reader/preview/freeze/批准形成新 attempt，不在原页面补填后重试 |
| 无法排除 SAVE2 已派发，或回包/页面/ledger 不一致 | 保存结果无法证明 | `execution_state=unknown`；停批并人工核对，禁止补填后再次保存 |

### 10.4 未知状态（UNKNOWN）

| 条件 | 处理 |
|------|------|
| 动作派发后结果不确定 | `execution_state=unknown`，`manual_review_required=true` |
| 断线/超时/页面丢失 | 停批，不得自动重试 |

## 12. 思考补充

> **`PASSIVE_ONLY / NEEDS_LIVE_EVIDENCE`**：本章只保存待验证的产品脑暴，不是可执行操作、默认值或生产 recipe。任何条目必须先取得真实页面/接口证据、进入主合同和冻结 Schema 后才能实施；与 §1–§11 冲突时，以前文当前主线为准。

### 12.1 需求完整性评估

经分析，用户补充的 8 项内容**覆盖了核心批量编辑场景的主要缺失**，但仍有以下可补充点：

#### 12.1.1 缺失的字段属性补充

| 字段/属性 | 建议处理方式 | 说明 |
|-----------|--------------|------|
| **产品分组** | 保持原值 / 方案配置 | 分组可批量指定，建议同「保持原值」模式 |
| **主图视频** | 按冻结视频策略生成/选择并写入 | 属于每件必经视频阶段的可用投放位；不能以保持原值冒充视频阶段完成 |
| **详细页视频** | 按冻结视频策略生成/选择并写入 | 若冻结策略选择该投放位，必须形成稳定视频身份、字段读回和动作回执 |
| **尺码表映射** | 保持原值 / 方案配置 | 某些类目需要尺码表，建议随类目关联 |
| **参考价格（市场价）** | 保持原值 / 方案配置 | 部分类目有参考价字段 |
| **重量单位** | 保持原值 / 方案配置 | g/kg 切换，店小秘默认 kg |
| **体积重计算** | 保持原值 / 启用配置 | 部分物流按体积重计费 |
| **EAN/UPC 条码** | 保持原值 / 方案配置 | 商品条码字段 |
| **退换货政策** | 保持原值 / 方案配置 | 部分类目必填 |
| **包装类型** | 保持原值 / 方案配置 | 影响物流属性展示 |

#### 12.1.2 变种自定义名称的扩展场景

|------|----------|
| 前缀 + 自增长数字 | 用户描述的场景，已实现 |

#### 12.1.7 标题处理的扩展

| 场景 | 处理方式 |
|------|----------|

#### 12.1.8 批量编辑的全局翻译时机

旧“全部商品填写完再统一翻译”的批次级方案已 `SUPERSEDED`，不得进入生产。当前只允许在**每件商品内部**完成冻结字段准备后，按 `video → HVD checkpoint → wholesale → HVD checkpoint → translation → HVD checkpoint` 执行；翻译完成并逐字段读回后，该商品才可进入 FIRST_SAVE。

### 12.2 当前每件商品翻译闭环

```
当前商品 0–10 分区字段准备完成
    → 视频动作与 HVD checkpoint
    → 批发填写/关系验证与 HVD checkpoint
    → 对当前商品执行翻译
    ├── 产品标题 → 英文标题
    ├── PC端描述 → 英文描述
    ├── 无线端描述 → 英文描述

    ├── 变种自定义名称 → 英文
    └── 其他自然语言字段 → 英文
    → 翻译结果逐字段回填和读回
    → 当前商品 11 区 aggregate/final verify
    → FIRST_SAVE
```
