# 店小秘半托管执行器可交付化回归矩阵

## 交付基线

- 当前基线日期：2026-07-17；实际提交以待合并分支最终 HEAD 为准，不能沿用旧 commit 或旧 portable。
- 交付模式：本地工作台 + 可见真实浏览器 + 持久化 Browser Agent + 两段式状态机；当前生产交付为 `BLOCKED`。
- 设计支持模式：`probe`、`dry_run`、`claim_only`、`single_save`、`batch_save`；当前源码 release surface 仅包含受控 Stage A `claim_only` 与 Stage B `single_save`，二者仍需全部 L0–L3、两段式、状态一致性、mutation ledger 和同 HEAD package 门禁。
- 禁止动作：发布、立即发布、继续发布、保存并发布、保存并移入待发布、移入待发布
- 真实写入边界：Stage A/B 分别使用服务端审批租约；L2 通过本身不能授权 mutation，旧 `single_save` 证据不能反向放行 Stage A。

## 不可退化项

| 领域 | 不可退化要求 |
| --- | --- |
| 店铺边界 | 任务、Stage A 来源、Stage B 商品快照和页面观察到的店铺必须一致；不得硬编码或跨店铺复用证据。 |
| 商品归属 | Stage B 只能操作当前 Stage A 已认领并完成商品箱验证的同一商品；来源/商品/任务任一绑定漂移必须停止。 |
| 发布隔离 | 任意发布相关按钮、弹窗、URL、网络请求信号都必须 E999 停止。 |
| 模板完整性 | `dxm_reference_templates` required 分区缺名称或页面未命中时不得进入保存。 |
| 图片证据 | 欧盟外包装图必须证明使用了配置文件名；营销图必须证明白底处理。 |
| 保存证据 | 保存成功、`published=false`、未发布校验截图必须同时存在。 |
| 报告证据 | report summary 必须保留 workflow results、模板解析、保存结果和证据路径。 |
| 状态一致性 | `dxm_state_consistency.v1` 必须无 task/job/report/exception violation；late result 不得覆盖人工复核或新状态。 |
| Mutation 幂等 | 稳定 mutation ID 必须进入持久化 ledger；`DISPATCHING` 崩溃恢复为 `UNKNOWN`，禁止自动重试。 |
| 实时身份 | 点击前重查 runtime、session、精确页面、目标、审批租约和 lifecycle owner；授权后的漂移必须阻断。 |

## 四级回归

| 等级 | 目标 | 是否访问店小秘 | 是否写入 | 触发条件 | 通过标准 |
| --- | --- | --- | --- | --- | --- |
| L0 | 纯代码回归 | 否 | 否 | 每次代码改动 | 后端测试全绿，前端 build 通过。 |

## 重点真实页面证据

### 欧盟外包装图

- 配置来源：`image.eu_outer_package_filename`
- 必须记录：图片银行搜索词、选中图片文本、选中项缩略图状态、槽位回填后状态。
- 通过标准：选中项文件名与配置文件名一致，或结果中明确 `filename_matched=true`。

### 营销图白底

- 策略：`marketing_images_strategy=generate`
- 必须记录：生成前营销图状态、生成后 1:1/3:4 图片状态、图片工具菜单中“图片白底”、白底弹窗“一键白底”点击结果。
- 通过标准：`1:1白底图` 与 `3:4场景图` 均有图片，且白底处理结果为成功或已处理。

### 店小秘引用模板

- 必须记录：`dxm_reference_templates_resolved` 和 `dxm_reference_template_results`
- 通过标准：required section 均 `ok=true`；optional 未命中必须记录 reason，不能静默消失。

### 保存与未发布证明

- 必须记录：保存按钮定位结果、保存成功文案、保存相关接口响应或 HAR 摘要、未发布校验截图。
- 证据等级：
  - A：页面截图 + report `published=false` + 保存接口/HAR + 无 publish 网络。
  - B：页面截图 + report `published=false`，但未捕获保存接口。
  - C：缺保存截图或缺未发布校验，不可交付。

## 真实 L3 执行前检查

- Stage A 与 Stage B 各自获得用户明确确认和服务端审批租约，不能复用。
- L2 `data_acquisition` 与 `draft_box` 最新真实只读 probe 均为 `passed`，且来自同一 `evidence_binding.run_id` / session / script / git head。
- 当前登录态有效，且无需绕过验证码。
- Stage A 模式/场景为受控 `claim_only`；Stage B 模式/场景为受控 `single_save` / `SMT_SEMI_MANAGED_SAVE_ONLY`。
- Stage B 的商品、店铺、来源和商品箱证明与已完成 Stage A 快照完全一致。
- 所有 required 模板、图片、半托管字段配置通过。
- 发布隔离预检通过。
- Browser Agent 实时 session/page/target 身份、lifecycle owner 和审批租约均仍有效。
- mutation ledger 中不存在同一动作的 `DISPATCHING`、`UNKNOWN` 或未完成记录。

## 最终交付门禁

- 后端 `pytest -q` 全绿。
- 前端 `npm run build` 通过。
- L0/L1 回归完成，且工作台 L1 显示 `passed`。
- L2 只读 probe 有双目标真实通过记录，并共享同轮次 evidence binding；若只存在 mock 证据，工作台必须显示“离线证据/不满足真实页面 L2 放行条件”；若只有单目标通过，必须显示“部分完成”；任一真实目标失败、缺失 binding 或 binding 不一致必须显示失败并阻断 L3。
- L3 必须有同一商品、同一当前 portable 的 Stage A/Stage B 最新验收记录；不得只凭人工批准、旧保存记录或单阶段成功进入真实写操作。
- `dxm_two_stage_acceptance.v1` 必须 `passed=true`，`missing_codes=[]`。
- `dxm_state_consistency.v1` 必须 `consistent=true`，`violation_codes=[]`，且审计任务非空。
- mutation ledger 必须无 `UNKNOWN`/未对账动作；崩溃恢复记录不能通过自动重试消除。
- 前端原型经用户确认。
- git 工作区干净并提交；runtime/build/portable/验收记录必须指向同一 HEAD，portable SHA-256 和 packaged smoke 已记录。
