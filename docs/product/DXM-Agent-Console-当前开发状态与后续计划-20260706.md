# DXM Agent Console 当前开发状态与后续计划

更新时间：2026-07-06

## 1. 当前最终目标

把 DXM Agent Console 做到可交付客户正常使用的生产级状态。核心不是诊断台，也不是演示工具，而是一个能控制真实浏览器完成店小秘自动化的桌面控制台。

业务主流程分为两大段：

1. 待认领商品入箱：从店小秘已有待认领商品列表中选择真实商品，认领到商品箱。
2. 商品箱编辑只保存：从商品箱商品进入编辑页，按模板填写配置，只点击保存，不发布、不批量、不无人值守。

当前默认安全边界：

- 允许：受控 `claim_only`、受控 `single_save`。
- 禁止：发布、批量保存、无人值守批量写入。
- 交付前必须有真实店小秘证据链：认领成功、商品箱验证成功、保存成功、未发布证明、保存网络回包或 HAR 证据、证据路径。

这说明当前“保存前不写入”的安全门禁已经可用。

### 3.3 前端任务启动链路已修复

问题：

- 当前任务页原来没有 `onStartTask`。
- 用户点击“启动/继续”实际只是跳到浏览器现场，没有调用 `/api/tasks/{id}/start`。
- 这会导致用户以为系统开始执行，但实际只是打开页面。

本轮修复：

- `ProductTasksPage.tsx` 增加 `onStartTask`。
- `start` 决策从 `actions.onShowConsole` 改成 `actions.onStartTask`。
- `App.tsx` 在 `product_tasks` 路由传入 `onStartTask={startSelectedTask}`。

验证：

- `test_frontend_demo_workflow_contract.py` 全量通过：`207 passed`
- `npm run build` 通过

### 3.4 已定位真实第一段失败根因

本轮创建并启动真实任务：

- 任务：`#181`
- 模式：待认领商品入箱
- 商品：`Pierrot怪胎马戏团游戏二次元周边相框画摆件学生收藏礼物`
- 来源链接：`https://detail.1688.com/offer/1065217744897.html`

真实执行结果：

- 认领动作返回成功。
- 店小秘页面弹窗显示：`速卖通采集认领执行完成，成功 1 条，失败 0 条，跳过重复数据 0 条`
- 系统随后进入“确认商品箱商品”。
- 失败原因：打开商品箱页面时 `Page.goto` 等待 `commit` 超时。

结论：

- 第一段的“点击认领”很可能已经成功。
- 当前失败不是保存或发布失败。
- 系统没有进入编辑页，没有保存，没有发布。
- 根因集中在“从待认领页面切换到商品箱页面”的导航稳定性。

### 3.5 已对商品箱导航超时做最小修复

问题：

- 可见真实浏览器中，原生地址栏导航没有稳定生效。
- 后续 `page.goto(... wait_until='commit', timeout=15000)` 超时会直接把第一段判失败。
- 但真实环境里页面可能已经开始进入目标 URL，只是 Playwright `goto` 没拿到 commit。

本轮修复：

- 在 `_verify_draft_box_claim` 中增加降级逻辑：
  - 仅限可见浏览器从待认领页切商品箱。
  - 如果 `goto` 超时，但当前 URL 已经是目标商品箱 URL，则记录事件并继续等待页面稳定。
  - 如果 URL 没切过去，仍然失败，不做误判通过。

验证：

- 新增红灯测试先失败，证明旧实现会直接抛超时。
- 修复后相关测试通过：
  - `test_verify_draft_box_claim_continues_when_visible_commit_goto_times_out_after_url_changes`
  - `test_verify_draft_box_claim_from_visible_data_acquisition_uses_commit_navigation`
  - `test_verify_draft_box_claim_from_visible_data_acquisition_prefers_native_address_navigation`
- 结果：`3 passed`

风险：

- 需要继续增强地址栏输入后的验证和重试策略。

### 5.2 第二段保存证据缺失

现象：

- 历史当前任务 `#141` 是 `needs_manual_review`。
- 没有保存结果、未发布证明、网络保存回包。

当前处理：

风险：

- 必须以证据为准，不靠推测。

### 5.3 真实浏览器运行稳定性仍是长期卡点

长期现象：

- 店小秘页面偶发 loading。
- 弹窗、遮罩、广告、引导会阻断操作。
- 双显示器、非全屏、缩放比例会影响原生点击坐标。
- Playwright 与真实可见 Chrome 混合控制时，导航和 DevTools 可能超时。

当前处理方式：

- 采用真实浏览器可见窗口。
- 增加 HUD 实时进度。
- 使用 DOM、截图、网络、SQLite 报告、workflow_worker JSON 多源证据定位。
- 对超时采用条件判断，不简单延长固定等待。

仍需加强：

- 启动时识别窗口位置和显示器。
- 导航后以 DOM/URL/标题/关键按钮共同判断页面是否可用。
- 浏览器 agent 保持常开，不因单次任务失败闪退。
- 异常后给用户明确恢复动作。

### 5.4 前端产品路径与后端真实能力曾经脱节

长期问题：

- 后端 API 有能力，但前端按钮没有接真实启动。

## 6. 一直存在的深层卡点

### 6.1 技术概念下沉过多

表现：

- 用户会看到 L2、L3、probe、HAR、run-id、greenlet、Internal Server Error。
- 普通用户无法判断自己该点哪里。

处理方式：

- 菜单改成业务路径。
- 文案逐步替换成待认领商品、商品箱、编辑保存。
- 技术细节收进维护区。

还未彻底完成：

- 部分旧组件仍保留工程词。
- 日志面板和报告页仍可能展示底层错误。

### 6.2 “采集”一词造成业务误解

真实业务不是系统去外部采集商品，而是处理店小秘里已有待认领商品。

处理方式：

- 用户侧改为“待认领商品”。
- 后端内部暂时仍有 `data_acquisition` 命名，短期不大改架构。

后续建议：

- UI 和文档彻底隐藏“采集”。
- 后端可以逐步增加 `claim_inbox` / `pending_claim` 别名，降低维护误读。

### 6.3 真实网站自动化天然不稳定

店小秘不是我们控制的系统，页面结构、弹窗、加载、按钮位置、异步请求都会变。

当前策略：

- 不用截图假演示。
- 不绕过 UI 直接写本地数据。
- 每一步必须有证据。
- 失败时 fail-closed，不保存、不发布。

代价：

- 开发速度慢。
- 真实验收容易暴露新边界。
- 必须持续做针对性稳定性补强。

## 9. 什么时候算任务完成

   - 登录店小秘
   - 选择待认领商品

   - 保存成功

   - L3 passed
