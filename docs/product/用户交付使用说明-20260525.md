# 用户交付使用说明 - 2026-05-25

## 交付结论

当前可交付给内部验收的是本地/内网安全诊断工作台，用于查看配置、任务、证据、L2 只读诊断和 L3 阻断原因。

当前不可交付的是店小秘真实无人值守保存/写入。真实 L2 双目标只读 probe 未通过前，真实 `claim_only` / `single_save` / `batch_save` 必须保持阻断。

## Windows 启动

1. 打开解压后的项目根目录，也就是包含 `README.md` 的目录；下文记为 `<PROJECT_ROOT>`。
2. 运行环境检查：

```bat
cd /d <PROJECT_ROOT>
scripts\start-mvp.bat --check
```

3. 检查通过后启动：

```bat
scripts\start-mvp.bat
```

4. 浏览器打开：

```text
http://127.0.0.1:5173
```

5. 停止服务：关闭 `DXM Backend Service` / `DXM Frontend Service`（中文可理解为 DXM 后端服务 / DXM 前端服务）两个 CMD 窗口。

## 用户可做的事

- 查看当前任务、商品、模板、证据、报告和异常。
- 查看 L0/L1/L2/L3 门禁状态。
- 在 L2 未通过时查看只读失败诊断。
- 复核真实保存为何被阻断。
- 在“报告中心”查看最近交付自检摘要、报告路径、真实写入阻断状态和当前证据；导出能力尚未接入，不作为本次交付承诺。

## 用户不能做的事

- 不能在当前状态启动真实 `claim_only` / `single_save` / `batch_save`。
- 不能绕过 L2 真实双目标只读 probe。
- 不能把 mock 或 fallback 数据当成真实页面通过证据。
- 不能宣称当前版本已经完成真实无人值守保存交付。

## 放行前置

真实保存交付必须同时满足：

- L2 `data_acquisition` 与 `draft_box` 两个真实目标同轮次通过；两份证据必须共享同一个 `evidence_binding.run_id`、`script_sha256`、`git_head` 和 session fingerprint。
- L2 证据无写请求、非只读请求、禁用 URL、WebSocket 或登录态异常。
- L3 由服务端校验人工批准令牌。
- L3 金丝雀产生保存成功、未发布证明、截图和 network/HAR 保存响应证据。

## 验收命令

推荐给验收人的本地工作台一键自检：

```bat
scripts\final-delivery-check.bat
```

它会依次执行启动前检查、后端全量测试、前端生产构建、L1 selector replay、`git diff --check` 和浏览器 QA，并生成：

- `outputs/final-delivery-check/final-delivery-check.md`
- `outputs/final-delivery-check/final-delivery-check.json`

报告顶部会分别显示“本地工作台自检结果”和“真实 DXM 写入放行状态”。浏览器 QA 会临时启动隔离的当前源码后端和前端预览服务，避免误测 8000/5173 上的旧进程；不需要先手动启动 `scripts\start-mvp.bat`。也可以按下面的单项命令逐步检查。

当前版本的验收成功标准是：默认验收要求 `Local workbench check: PASS`、`Browser QA: PASS`、`Source package check: NOT_REQUIRED`，并且 `Real DXM write readiness: BLOCKED`；源码发布包验收才要求 `Source package check: PASS`。`BLOCKED` 是当前预期安全态，表示真实 L2/L3 证据不足，不能把它当成真实写入可用。

如果要验收源码发布包，再运行：

```bat
scripts\final-delivery-check.bat -RequireCleanWorktree
```

该模式要求 git 工作区干净；当前仍在开发中时会显示 `Source package check: FAIL`，不影响你查看本地工作台自检是否通过。

查看自检参数：

```bat
scripts\final-delivery-check.bat --help
```

正式验收不要使用 `-SkipBrowserQA`。

```bat
scripts\start-mvp.bat --check
```

浏览器 QA 会生成：

- `outputs/browser-checks/qa-browser-check.json`
- `outputs/browser-checks/qa-task-center.png`
- `outputs/browser-checks/qa-execution-console.png`
- `outputs/browser-checks/qa-report-center.png`
- `outputs/browser-checks/qa-mobile-task-center.png`
- `outputs/browser-checks/qa-console.jsonl`
- `outputs/browser-checks/qa-network.json`
- `outputs/browser-checks/qa-blocked-actions.json`

其中 `qa-browser-check.json` 会记录浏览器/OS/git/script hash，并断言无 console error、无网络失败、无 4xx/5xx、无非 GET、无外部 origin、移动端无横向溢出；`qa-blocked-actions.json` 会记录本地启动与直接 DXM 写入端点的 403 阻断结果。

## 常见失败定位

- `scripts\start-mvp.bat --check` 失败：先看 `data\start-mvp.log`；缺 Python/Node/npm/curl 时按日志提示补环境，前端依赖安装失败看 `data\npm-install.log`。
- 启动提示 8000 或 5173 端口占用：关闭已有 `DXM Backend Service` / `DXM Frontend Service` CMD 窗口，或确认占用者就是本项目服务。
- 启动最后显示 `STARTED_WITH_WARNINGS`：服务窗口已打开，但后端或前端健康检查暂未响应；先看 `data\backend.log` / `data\frontend.log`，不要把它当成完全启动成功。
- 浏览器 QA 失败：先看 `outputs/final-delivery-check\browser-workbench-qa.stdout.log` / `.stderr.log`，再看 `outputs/final-delivery-check\browser-checks\qa-browser-check.json` 的失败 assertion；本机必须安装 Chrome 或 Edge。
- 最终自检没有生成 `final-delivery-check.md`：先看控制台最后一条错误，再运行 `scripts\start-mvp.bat --check` 定位缺失依赖。
- `Source package check: FAIL`：只在 `-RequireCleanWorktree` 模式下代表工作区不干净，运行 `git status --short` 查看未提交改动；不表示真实 DXM 可以写入。
- `Real DXM write readiness: BLOCKED`：这是当前预期安全状态；不要为了让报告“全绿”去绕过 L2/L3 门禁。
