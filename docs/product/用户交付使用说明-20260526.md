## Windows 单窗口启动

1. 打开解压后的项目根目录，也就是包含 `README.md` 的目录；下文记为 `<PROJECT_ROOT>`。
2. 运行环境检查：

```bat
cd /d <PROJECT_ROOT>
scripts\start-mvp.bat --check
```

3. 检查通过后启动：

```bat
scripts\start-mvp.bat
```

4. 保留当前启动器窗口。后端和前端会由这个窗口托管；健康检查通过后会自动打开工作台页面。如果 5173 端口被占用，启动器会使用附近空闲端口，实际地址以启动器输出和 `data\start-mvp.log` 为准。
5. 默认浏览器地址：

```text
http://127.0.0.1:5173
```

6. 停止服务：关闭当前启动器窗口，或在启动器窗口按 `Ctrl+C`。脚本退出时会尽力停止后端和前端子进程树。

启动日志：

- `data\start-mvp.log`：启动器、端口和健康检查。
- `data\backend.log`：后端 API、任务和运行时控制。
- `data\frontend.log`：前端 Vite 服务。
- `data\npm-install.log`：首次依赖安装。

## 真实 single_save 操作流程

按以下顺序执行。不要跳过 L2/L3 门禁，也不要用本地 `dry_run` 演示批次代替真实验收。

### 第 1 步：打开真实店小秘登录页并登录

1. 启动工作台后进入“操作引导”。
2. 在“打开真实 DXM 浏览器并确认登录”步骤点击“打开登录页”。
3. 按弹窗输入店小秘账号和密码。账号密码只用于本次真实店小秘登录，不保存到配置中心。
4. 系统会打开独立浏览器并访问 `https://www.dianxiaomi.com/`。
5. 在这个真实店小秘浏览器窗口中完成人工登录、验证码、二次确认或账号选择。
6. 回到工作台确认“DXM 登录”状态变为已登录或 `login_success` / `logged_in`。

如果需要观察浏览器画面、日志和网络响应，再进入“执行控制台”。执行控制台的“打开真实浏览器”用于任务执行观察；真实保存仍受 L2/L3 门禁保护。

### 第 2 步：在配置中心补齐店小秘编辑页分区

进入“配置中心”，按页面分区填写。每个分区保存后，右侧“本次任务实际取值预览”会显示最终取值来源。

需要逐项核对的分区：

- 店铺与任务基础：店铺、执行模式、绑定类目、认领标记。
- 类目与标题：目标类目、类目关键词、DXM 类目 ID、标题覆盖和标题策略。
- SKU / 价格 / 库存：SKU 编码、库存、JIT 库存、SKU 规则和变种策略。
- 价格策略：商品价、供货价、价格来源、倍率或固定价。
- 图片与素材：EU 外包装图、营销图策略、主图策略和本地素材目录。
- 包装物流：重量、长宽高、物流属性、运费模板和服务模板。
- 合规 / 海关：报关品名、材质、用途、品牌和合规声明。
- 半托管：商品价、JIT 库存、是否原包装、半托管长宽高、货号策略和条码策略。
- 店小秘引用模板：属性信息、描述、运费、服务、欧盟责任人、制造商、合规模板和半托管模板。

保存规则：

- 有当前任务时，优先用“仅本次任务使用”，避免影响后续任务。
- 需要沉淀为店铺或类目默认值时，再用“保存为店铺模板”。
- 配置预检显示“配置还不能启动真实保存”时，必须先补齐缺失项；系统不会进入真实保存。

### 第 3 步：在任务中心创建 single_save

1. 进入“任务中心”。
2. 在“创建真实任务”区域选择店铺。当前受控真实写入门禁要求店铺为 `Dang Kang`。
3. 在执行模式中选择 `L3 single_save`。不要选择本地 `dry_run` 演示批次作为真实交付依据。
4. 在商品队列中只选择要核验的真实商品。当前可交付范围是单商品受控保存；如列表里有多个商品，按受控口径分批创建，不把它解释为无人值守批量。
5. 点击“创建真实任务”，然后在任务列表中选中刚创建的任务。

如果“启动”按钮显示以下状态，按提示处理：

- `配置未完成，禁止启动`：回到“配置中心”补齐缺失字段。
- `L2 未通过，禁止启动` / `L2 失败，禁止启动`：查看“L2/L3 决策说明”和只读失败诊断。
- `L3 保持锁定，禁止启动`：L2 或人工批准未满足，不能绕过。
- `未发布，禁止启动`：当前模式不是已放行的 `single_save`。

### 第 4 步：人工批准并启动保存金丝雀

当任务满足配置预检、L2 `passed` 和 `single_save` 模式后，“当前任务操作”按钮会显示“批准并启动真实金丝雀”。

1. 点击“批准并启动真实金丝雀”。
2. 在弹窗中输入 L3 批准人标识，例如 `ops-owner`。
3. 系统会向后端申请服务端批准令牌，并用确认口令 `CONFIRM_DXM_SAVE_ONLY` 启动任务。
4. 后端只允许通过任务 runner 证据链执行真实写入；直接调用店小秘写入端点会被 403 阻断。

这一步只批准受控 `single_save`。它不批准 `claim_only`、`batch_save`、无人值守批量或发布。

### 第 5 步：在执行控制台观察真实浏览器和日志

任务启动后会自动进入“执行控制台”。你需要观察这些区域：

- “真实浏览器”：显示独立店小秘浏览器的当前 URL、截图、浏览器数据目录和发布隔离状态。
- “自动操作轨迹”：显示点击、填写、上传、等待、保存等动作。
- “网络响应”：关注保存接口响应，尤其是 `popChoiceProduct/add.json`。
- “实时日志中心”：切换“后端 / 前端 / 启动器 / 任务 / 浏览器 Agent”，可搜索 `保存`、`error`、`add.json`。
- “执行步骤明细”：确认步骤按状态机推进，没有跳过 L2/L3 门禁。

如果真实浏览器停留在登录页、验证码页或页面加载异常，先人工处理登录态或查看 L2 诊断；不要手动点击发布、提交发布、保存并发布等按钮。

### 第 6 步：核对只保存不发布的结果

任务完成后进入“报告中心”和“证据中心”，核对：

- 保存接口返回成功，例如 `code=0`。
- 报告中的 `published=false`。
- 有未发布证明、截图、保存响应或 HAR/network 证据。
- 保存隔离摘要显示发布动作未开放或发布隔离通过。
- 异常池没有阻断当前任务的未处理异常。

只有同时满足“保存成功”和“未发布”时，才把这次 `single_save` 视为通过。不能把这次结果扩大解释为批量保存、无人值守运行或发布放行。

## 放行前置

- L2 证据无写请求、非只读请求、禁用 URL、WebSocket 或登录态异常。

- L3 金丝雀产生保存成功、未发布证明、截图和 network/HAR 保存响应证据。

## 验收命令

推荐给验收人的自动化工作台一键自检：

```bat
scripts\final-delivery-check.bat
```

它会依次执行启动前检查、后端全量测试、前端生产构建、L1 selector replay、`git diff --check` 和浏览器 QA，并生成：

- `outputs/final-delivery-check/final-delivery-check.md`
- `outputs/final-delivery-check/final-delivery-check.json`

报告顶部会分别显示“自动化工作台自检结果”和“真实 DXM 写入放行状态”。浏览器 QA 会临时启动隔离的当前源码后端和前端预览服务，避免误测 8000/5173 上的旧进程；不需要先手动启动 `scripts\start-mvp.bat`。也可以按下面的单项命令逐步检查。

当前版本的源码包验收成功标准是：`Local workbench check: PASS`、`Browser QA: PASS`、`Final report center QA: PASS`、`Source package check: PASS`，并按 L2/L3 门禁计算 `Real DXM write readiness`。截至 2026-06-03 09:46，当前交付态为 `READY`，且只代表受控 `single_save`。未来若显示 `BLOCKED`，通常表示 L2 证据过期、L2 未过或 L3 未放行，不能把它当成真实写入可用。

## L2 allowlist 人工评审包

最终自检报告会在 `L2 Allowlist Review Candidates` 段落列出可能属于只读启动依赖的 GET/XHR 请求。任务中心也会在 L2 失败诊断里展示同一类候选请求，便于操作者不离开页面就知道下一步要评审哪些路径。

这些候选项只代表“需要人工评审”，不是放行结论：

- `review_only=True`
- `allowlist_applied=False`
- 不自动放行 L2/L3

人工评审时只能考虑显式、最小、可审计的只读依赖；不能放行 POST、PUT、PATCH、DELETE、WebSocket、EventSource，也不能放行命中 `save/publish/claim/remark/note` 等禁用关键词的 URL。不能为了让报告全绿而绕过 L2/L3 门禁。

每次运行最终自检会同时生成可填写的人工评审模板：

- `outputs/final-delivery-check/l2-allowlist-review-template.md`
- `outputs/final-delivery-check/l2-allowlist-review-template.json`

最终自检报告和报告中心会同时展示这两份模板的 `sha256` 哈希。评审、归档或转交模板时，应核对路径、Git HEAD 和哈希都对应同一次 `final-delivery-check` 输出；如果模板被填写或改动，必须保留填写后的新文件和新哈希，不能用已改动模板冒充原始自检模板。

评审记录至少要填写 `reviewer`、`reviewed_at`、`decision`、`rationale`、`approved_scope`、`residual_risk`。批准项还必须写明最小化范围、到期时间或后续复核策略，并在代码/配置变更后重新跑同一批真实 L2 双目标；模板本身不是 L2 通过证明。

## 常见失败定位

- `scripts\start-mvp.bat --check` 失败：先看 `data\start-mvp.log`；缺 Python/Node/npm/curl 时按日志提示补环境，前端依赖安装失败看 `data\npm-install.log`。
- 启动提示 8000 端口占用：关闭已有启动器窗口，或确认占用者就是本项目后端服务。5173 被占用时启动器会自动选择附近空闲前端端口，实际访问地址以启动器输出为准。
- 启动最后显示 `STARTED_WITH_WARNINGS`：服务窗口已打开，但后端或前端健康检查暂未响应；先看 `data\backend.log` / `data\frontend.log`，不要把它当成完全启动成功。
- 浏览器 QA 失败：先看 `outputs/final-delivery-check\browser-workbench-qa.stdout.log` / `.stderr.log`，再看 `outputs/final-delivery-check\browser-checks\qa-browser-check.json` 的失败 assertion；本机必须安装 Chrome 或 Edge。
- 最终自检没有生成 `final-delivery-check.md`：先看控制台最后一条错误，再运行 `scripts\start-mvp.bat --check` 定位缺失依赖。
- `Source package check: FAIL`：只在 `-RequireCleanWorktree` 模式下代表工作区不干净，运行 `git status --short` 查看未提交改动；不表示真实 DXM 可以写入。
- `Real DXM write readiness: BLOCKED`：表示当次验收没有真实写入放行；不要为了让报告“全绿”去绕过 L2/L3 门禁。
