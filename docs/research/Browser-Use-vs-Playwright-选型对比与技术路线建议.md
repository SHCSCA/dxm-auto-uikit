# Browser Use vs 自建 Playwright 选型对比与技术路线建议

> 项目：店小秘自动刊登助手（dxm-auto-uikit）
> 场景：速卖通 POP / 半托管，本地运行、可视化执行、可人工接管、模板驱动、异常可追溯
> 结论先行：**上层业务系统自建，下层浏览器执行层优先自建 Playwright；Browser Use 作为原型验证/增强候选，而不是主底座。**

---

## 1. 背景

当前项目的目标，不是做一个“自动点页面的脚本”，而是做一套围绕店小秘的自动刊登系统，核心要求有 5 个：

1. **本地运行**：用户不愿把店小秘账号和流程完全托管到云端。
2. **执行可见**：要有实时浏览器执行区，用户能看到程序在做什么。
3. **可人工接管**：遇到验证码、风控、异常字段时，能暂停并接管。
4. **模板驱动**：字段建模完整，模板中心是核心资产。
5. **异常可追溯**：失败不是一句“发布失败”，而是知道哪个字段域、哪个步骤、哪张图、哪个模板出了问题。

因此，这个产品的真正核心不是“浏览器会不会点”，而是：

- 商品建模
- 模板中心
- 任务状态机
- 字段域驱动执行
- 证据/异常体系

浏览器执行层只是其中一层，不是全部。

---

## 2. 对比对象定义

### 方案 A：Browser Use Cloud
使用 Browser Use Cloud / Agent / Stealth Browser / Human-in-the-loop / Live Preview 等能力，快速构建网页自动化执行层。

### 方案 B：自建 Playwright 执行层
基于本地客户端 + 本地 Playwright + 本地 Session 管理 + 本地任务引擎，自建店小秘自动化执行层。

---

## 3. 选型对比结论总表

| 维度 | Browser Use Cloud | 自建 Playwright | 结论 |
|---|---|---|---|
| 启动速度 | 快 | 中等 | Browser Use 胜 |
| 本地可信度 | 弱 | 强 | Playwright 胜 |
| 与本项目定位契合度 | 中 | 高 | Playwright 胜 |
| 可视化执行 | 强 | 可自建 | Browser Use 略胜 |
| 人工接管 | 强 | 可自建 | Browser Use 略胜 |
| 登录态/会话本地掌控 | 弱~中 | 强 | Playwright 胜 |
| 字段级可控执行 | 中 | 强 | Playwright 胜 |
| 异常归因可定制 | 中 | 强 | Playwright 胜 |
| 对店小秘专用适配 | 需要二次封装 | 天然适合 | Playwright 胜 |
| 成本可控性 | 持续订阅/API成本 | 主要是研发成本 | 看阶段 |
| 风控/反检测能力 | 强 | 取决于自建质量 | Browser Use 胜 |
| 长期架构掌控力 | 中 | 强 | Playwright 胜 |
| 适合做 MVP 演示 | 强 | 中 | Browser Use 胜 |
| 适合做长期商用本地版 | 一般 | 强 | Playwright 胜 |

**结论：**
- **短期演示/验证：Browser Use 有价值**
- **长期正式产品：自建 Playwright 更合适**
- **本项目最优路线：混合策略，但主架构必须掌握在自己手里**

---

## 4. Browser Use 的价值点

Browser Use 对本项目不是没用，而是“有用，但不该做主心骨”。

### 4.1 它最有价值的地方

#### 1）可视化浏览器与实时反馈
它原生就有：
- Live preview
- Streaming / live messages
- Recording
- Human in the loop

这与项目里的这些能力高度对应：
- RPA 实时执行区
- 证据面板
- 执行过程可见
- 人工接管

#### 2）浏览器基础设施成熟
它提供：
- Stealth 浏览器
- CAPTCHA 处理思路
- Proxy
- 云端托管环境

对 MVP 来说，能少踩很多底层坑。

#### 3）对“快速跑通”有帮助
如果目标是：
- 先做一个能演示的自动执行版本
- 先跑通登录、打开页面、填表、保存待发布
- 先验证用户是否真的认可“可视化自动刊登”这件事

那 Browser Use 非常适合做加速器。

---

## 5. Browser Use 的问题

### 5.1 与本项目“本地可信”定位天然冲突
这个项目有一个非常核心的商业前提：

> 用户不想把账号、会话、流程、数据完全交给云端托管。

而 Browser Use Cloud 的默认思路是：
- 云侧浏览器
- 云侧会话
- 云侧任务执行
- API 调度

这与“本地运行、真实店小秘页面登录、本地掌控”的定位不完全一致。

### 5.2 更偏自然语言任务，不是字段域强约束执行
Browser Use 更强的是：
- 给一个自然语言任务
- Agent 自主完成网页操作

但本项目真正需要的是：
- 字段域驱动
- 模板绑定
- 严格步骤树
- 精准日志归因
- 失败定位到字段/模板/步骤级

也就是：

> 我们要的是“业务系统驱动浏览器”，而不是“浏览器 Agent 反过来定义业务”。

### 5.3 长期成本与控制权问题
一旦核心执行层长期依赖第三方云能力，会带来：
- API 成本持续上涨
- 行为可控性下降
- 调试链路变长
- 部分细节能力被平台封装限制
- 本地版产品价值被削弱

---

## 6. 自建 Playwright 的价值点

### 6.1 完全契合当前产品结构
当前 dxm-auto-uikit 的文档，已经明确了这些结构：
- 模板中心
- 任务中心
- Task / Job / Step 状态机
- 异常池
- 日志与证据面板
- Dxm Adapter
- Playwright Worker

这套结构天然就是为自建执行器准备的。

### 6.2 字段域驱动更容易做扎实
比如：
- 标题域
- 类目域
- 资质域
- 主图域
- SKU/价格域
- 重量尺寸域
- 半托管报价域
- 欧盟责任人/制造商域

这些字段域在自建执行层里，可以直接做到：
- 每个字段有明确 source
- 每个动作有明确 selector
- 每个步骤有明确 evidence
- 每个失败有明确 error code

这正是商用能力核心。

### 6.3 本地登录、本地会话、本地证据链
用户在本地真实店小秘页面登录，整个链路都更符合信任模型：
- 登录态保存在本地
- Cookie / Storage 本地持有
- 执行证据本地落库
- 用户能直接看到浏览器过程

这对卖家来说，比“云端帮你自动操作”更可信。

---

## 7. 自建 Playwright 的问题

### 7.1 底层工作更脏
要自己处理：
- 浏览器生命周期
- Session 管理
- 页面等待策略
- 页面变动兼容
- 上传、滚动、弹窗、iframe
- 验证码暂停与接管
- 错误恢复

### 7.2 反检测能力起步不如 Browser Use
如果未来站点风控越来越严，纯自建 Playwright 可能要补：
- 浏览器指纹处理
- 代理策略
- 行为拟人化
- 页面探测规避

### 7.3 初版交付速度不如 Browser Use
纯自建更适合长期主义，不适合“临时提出一个产品，次日就要完整演示”。

---

## 8. 对 dxm-auto-uikit 的最终路线建议

## 8.1 最佳策略：主系统自建 + 执行层预留双引擎

### 核心原则
**业务中台一定自建，执行引擎允许插拔。**

也就是说：
- 商品模型、模板中心、任务状态机、异常池、证据体系，全都由我们自己掌控
- 浏览器执行层不要写死成某个厂商能力
- 定义一个统一的 `ExecutionEngine` 接口
- 先落地 `PlaywrightEngine`
- 后续可以补 `BrowserUseEngine`

### 为什么这样最优
这样做有 4 个好处：

1. **不丢控制权**
   - 业务规则永远掌握在我们手里

2. **先做本地可信主版本**
   - 符合产品定位

3. **未来可做增强版执行器**
   - 某些场景可切 Browser Use

4. **可根据场景动态选执行器**
   - 本地低风险任务 → Playwright
   - 复杂风控场景 / 演示版 / 高反爬站点 → Browser Use

## 9. 推荐实施路线（直接可执行）

## Phase 0：先冻结边界（现在）

目标：别再泛泛讨论，开始进入工程实现。

### 现在就确定三件事
1. **产品主路线：本地版优先**
2. **执行层策略：先 Playwright，接口上兼容 Browser Use**
3. **MVP 场景只做一条最短闭环**
   - 平台：速卖通
   - 场景：POP 优先
   - 结果：保存待发布优先

### 为什么 POP + 保存待发布优先
因为这条链路最短，最容易先跑通：
- 登录店小秘
- 选择店铺
- 导入商品数据
- 绑定模板
- 自动填标题、类目、图片、SKU、价格、运费模板
- 保存待发布
- 落日志、截图、异常

先不要一上来就死磕：
- 半托管全字段
- 自动发布
- 验证码自动解
- 云端订阅

这些都放后面。

## Phase 1：做本地 MVP 最小闭环（必须自建）

### 必做模块

#### 1）本地数据库
建议直接落地当前已设计好的核心表：
- stores
- sessions
- templates
- template_bindings
- products
- product_media
- product_variants
- product_pricing
- tasks
- jobs
- job_steps
- exceptions
- job_evidences
- job_logs

#### 2）模板中心 MVP
首版别做 18 套全开，先做高频模板：
- 标题模板
- 类目模板
- 图片模板
- SKU/价格模板
- 运费模板

#### 3）任务中心 MVP
要能完成：
- 创建任务
- 启动任务
- 暂停任务
- 终止任务
- 查看执行状态

#### 4）Playwright 执行器 MVP
能力先只做：
- 打开店小秘
- 检查登录态
- 进入创建商品页
- 按字段域顺序填表
- 上传图片
- 保存待发布
- 截图与日志

#### 5）右侧实时执行区 MVP
展示：
- 当前页面
- 当前商品
- 当前步骤
- 当前字段
- 当前动作
- 最新截图
- 错误提示

#### 6）异常池 MVP
先支持几类最常见错误：
- 类目映射失败
- 图片缺失/不合规
- 运费模板未匹配
- 页面元素缺失
- 登录失效

## Phase 2：补关键商用品质（仍以自建为主）

### 增强项
1. **人工接管模式**
   - 遇验证码 / 弹窗 / 风控时暂停
   - 用户操作后继续

2. **断点续跑**
   - 从失败商品/失败步骤继续

3. **证据系统增强**
   - DOM 快照
   - 操作轨迹
   - 录屏

4. **选择器配置中心**
   - 适应店小秘页面变化

5. **半托管链路**
   - 报价域
   - 重量尺寸域
   - 履约参数域
   - 责任主体域

---

## Phase 3：引入 Browser Use 作为增强引擎（可选）

在下面这些条件满足后，再引入 Browser Use，而不是现在就拿它当底座：

### 引入时机
- 本地 MVP 已跑通
- 我们已经验证用户真需要这个产品
- 自建执行器在某些场景成本太高
- 某些页面/站点反检测太强
- 需要更强的 live preview / cloud execution 能力

### 引入方式
**不是推翻自建，而是增加一个新引擎：**

- `PlaywrightEngine`：默认、本地版、主引擎
- `BrowserUseEngine`：增强版、实验版、云辅助引擎

### 适合 Browser Use 的具体场景
1. 演示版/销售版原型
2. 高风控页面的辅助执行
3. 复杂登录流或跨页面流程的快速验证
4. 需要更强浏览器基础设施的特殊任务

## 10. 技术架构建议（最终版）

### 10.1 必须稳定掌握在自己手里的层
这些绝不能外包给 Browser Use：
- 商品数据模型
- 模板中心
- 模板绑定规则
- 任务状态机
- 任务/步骤拆分
- 错误码体系
- 异常池逻辑
- 证据索引
- UI 交互状态

### 10.2 可以抽象成执行引擎接口的层
建议抽象接口：
- `start_session()`
- `check_login()`
- `open_create_product_page()`
- `fill_field(field_domain, payload)`
- `upload_media(media_type, files)`
- `save_as_draft()`
- `publish()`
- `take_screenshot()`
- `capture_dom()`
- `pause_for_manual_action()`
- `resume()`
- `stop()`

让业务层只调用接口，不依赖具体浏览器实现。

### 10.3 推荐默认技术栈
- **客户端 UI**：先 Electron + React（或者 Tauri + React，若更重视轻量）
- **本地后端**：Python + FastAPI
- **浏览器自动化**：Playwright（首选）
- **本地数据库**：SQLite
- **事件推送**：WebSocket
- **证据存储**：本地文件系统 + SQLite 索引
- **AI 服务**：后续外挂，不先耦合进主流程

---

## 11. 一句话路线结论

### 最终结论
**这项目不能把 Browser Use 当底座。**

正确姿势是：

> **用自建 Playwright 扛住正式产品的本地可信主架构；把 Browser Use 当成可插拔增强执行器，用于原型验证、特殊场景加速和后续能力扩展。**

## 13. 我给你的最终建议（最直接版）

如果你现在就要开始做：

### 该怎么选
- **正式产品路线：自建 Playwright**
- **原型/演示/增强验证：Browser Use 可接入，但不是必选**

### 该怎么干
1. 先用现有 PRD / 字段矩阵 / 表结构 / 技术图，直接开工 MVP
2. 浏览器执行层抽象接口，不写死
3. 默认实现 `PlaywrightEngine`
4. 后续如果遇到：
   - 风控太重
   - 演示要求太高
   - 某些流程云端更省事
   再补 `BrowserUseEngine`

## 14. 最后一句

**Browser Use 对这个项目有帮助，但它帮的是“浏览器执行基础设施”，不是“店小秘自动刊登业务系统本身”。**

所以别把方向搞反。

你真正该守住的，不是浏览器是谁开的，而是：
- 模板中心是不是你控制的
- 任务状态机是不是你定义的
- 异常池是不是你能追到字段域的
- 用户是不是信任这套系统

这才是产品能不能卖、能不能长期跑的关键。
