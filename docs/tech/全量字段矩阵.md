# 店小秘自动刊登助手 全量字段矩阵

> 版本：v0.1
> 目标：把“自动刊登”所需字段一次性拉全，避免后期因为字段缺漏导致产品重构。
> 适用范围：速卖通跨境 POP、速卖通半托管（含可扩展全托管/海外仓托管思路）

## 1. 设计原则

这份字段矩阵不是“商品编辑页字段列表”，而是整个系统的数据边界。

也就是说，凡是未来有可能影响：
- 自动创建商品
- 自动保存待发布
- 自动发布
- 模板复用
- 合规校验
- 定价报价
- 半托管报价提交
- 异常回退

的字段，都应该进入产品模型。

原则：
1. 先全量建模，再决定哪些在前台展示
2. 先支持模板中心，再支持单商品覆盖
3. POP 和半托管字段统一建模，但执行链路可以分开
4. 字段分为：基础字段 / 模板字段 / 场景字段 / 合规字段 / 平台特有字段

## 6. 产品实现建议

### 6.1 现在就要建模，但不一定现在就开放

也就是说：
- 数据库先建全
- 前台先开放高频字段
- 稀有字段放到“高级设置”或“模板中心”

### 6.2 执行层要按场景切换

同一个商品在不同发布场景，执行器要走不同流程：

```text
POP：
基础信息 → 类目属性 → 图片 → SKU → 运费模板 → 保存/发布

半托管：
基础信息 → 类目属性 → 图片 → SKU → 报价 → 重量尺寸 → 合规字段 → 提交
```

### 6.3 异常池要知道是哪个字段域出错

例如：
- E201 标题域错误
- E202 类目域错误
- E203 资质域错误
- E204 图片域错误
- E205 视频域错误
- E206 SKU域错误
- E207 定价域错误
- E208 物流域错误
- E209 合规域错误
- E210 半托管报价域错误

这样异常池才能真正可用。

## 7. 最终结论

你提到的这些字段必须全量考虑，判断是正确的。

不是因为所有字段都会在 v1 全部上线，
而是因为：
如果现在不按全量字段建模，后面每新增一个场景（半托管、报价、欧盟责任人、制造商、视频、营销图、白底图），都会把原架构打穿。

所以正确做法是：

1. 先按全量字段建模
2. 再按使用频率分层开放 UI
3. 再按场景拆执行链路
4. 再把高频字段抽成模板中心

一句话：
字段可以分阶段开放，但数据模型必须一次性考虑全。
